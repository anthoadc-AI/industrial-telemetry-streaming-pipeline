# Phase 3 Backlog

Items recorded during Phase 3 for a later task, with where they come from. Phase 2 items that carried over are in `docs/internal/phase2_backlog.md` and in section 8 of the Phase 2 closure report.

## For the design of Task 3.2 (ThingsBoard as the operations layer)

- **The ThingsBoard sink must tolerate tombstones with unknown keys on `telemetry.alarms`** (owner, 2026-10-02). The topic is compacted and keyed by `alarm_id`, and not every record on it is an alarm event: since `f28516f` the integration test `test_restore_after_real_compaction` writes one tombstone per partition with a reserved key (`it-roll-marker/<partition>`) to force a segment roll, and compaction itself turns superseded records into gaps. A tombstone has a null value and a key that need not match any alarm. The sink must skip such records (or treat them as deletions of an alarm it never saw) without failing, without dead-lettering them, and without blocking its consumer group. The alarm consumer's own restore already does this (`readActiveAlarms`: a tombstone deletes the key, a no-op for an unknown one).

## For Task 3.4 (architecture document)

- **A CLEARED event stays in the active segment until the next write to its partition** (owner, 2026-10-02). The broker evaluates `segment.ms` only when it appends to a partition, and the log cleaner never compacts the active segment. So on `telemetry.alarms`, the RAISED record of a cleared alarm is removed only after another record lands in the same partition and closes the segment holding the CLEARED. With alarms keyed by `alarm_id`, which contains a timestamp, which partition receives the next write is chance; on a quiet partition the RAISED/CLEARED pair can stay uncompacted indefinitely. This is not a correctness problem (readers keep the latest event per `alarm_id`, and the restore reads the CLEARED), but it means compaction does not bound the topic's size by time. Verified on 2026-10-02 on a scratch topic with `segment.ms` 1000 (no roll in 40 s without writes; the old record gone about 20 s after one unrelated write); root cause of the CI failure of run 37070295558, fixed in `5b28fd1`. `ARCHITECTURE.md` should state it under delivery semantics or the compaction policy, with the broker settings that govern it (`segment.ms`, `min.cleanable.dirty.ratio`, `log.cleaner.backoff.ms`).
- **`telemetry.alarms` is keyed by `alarm_id` but partitioned by asset** (owner, 2026-10-03, Task 3.2). The alarm consumer's producer uses `AssetPartitioner` (`processing/alarm_consumer/consumer.js`): the key stays the `alarm_id`, which compaction and the state restore need, while the partition is the default murmur2 partition of the `asset_id` (the key's first segment). Kafka orders records only within a partition, and the ThingsBoard sink's alarm mapping needs an asset's alarm events in production order: it applies an event only if it is newer than the last one applied for that asset and alarm type. With the default partitioner (partition from the whole `alarm_id`) an asset's alarms spread over partitions and a lagging or replaying reader drops older alarms; measured in Task 3.2 before the change: 19 of 48 alarms kept after a replay. Any other producer writing to `telemetry.alarms` must partition the same way. `ARCHITECTURE.md` should state this contract next to the compaction policy; dead letters from the consumer follow the same rule (keyed by `asset_id`).
- **`make run` keeps the pipeline running until it is stopped** (owner, 2026-10-03, review of Task 3.2). For STEP 0 of Task 3.4: the processes (sink, alarm consumer, bridge, simulator) must run until stopped, with no short `--duration`. The Task 3.2 review instructions used `--duration 1200`, and the consumer and the bridge stopped in the middle of the owner's review.
- **A simulator QoS 1 acknowledgement means Mosquitto accepted the message, not that the bridge got it** (owner, observed live 2026-10-03). With the bridge down, the simulator reported 600 messages sent and acknowledged and none reached Kafka. Why: Mosquitto runs with `persistence false`, and the bridge connects with a clean session (paho's MQTT 3.1.1 default, `clean_session=True`) under a client id that contains its process id, so no session outlives it; with no subscriber connected, the broker accepts each QoS 1 publish (the PUBACK the simulator counts) and drops it. `ARCHITECTURE.md` must state this hop's semantics: delivery from the simulator to Mosquitto is acknowledged, delivery from Mosquitto to the bridge happens only while the bridge is connected. A persistent session (fixed client id, `clean_session=False`, Mosquitto persistence on) would queue messages while the bridge is down, up to Mosquitto's queue limits; not implemented, listed with the other known limitations of the bridge (manual MQTT acknowledgement). Re-verified from the code on 2026-10-12 (DETENTE 3.3.h): paho-mqtt 2.1.0 turns `clean_session=None` into `True` for MQTT 3.1.1 (`paho/mqtt/client.py:784-785`) and the bridge does not pass it. Three additions: (1) in a container, with `init: true`, the bridge's process id repeats (`mqtt-to-kafka-bridge-7`), so its client id does not change across container restarts, which changes nothing while the session is clean, since Mosquitto discards the old session on every connect; (2) the same loss happens on paho's automatic reconnect after a network cut: what is published between the disconnection and the new subscription is lost; (3) these losses never appear in `$SYS/broker/publish/messages/dropped` (with no subscriber there is no client queue to overflow), so the bridge's drop monitor (`mqtt_messages_dropped`) does not see them. A persistent session would be bounded by the same per-client queue as a connected bridge (`max_queued_messages 60000`, `max_queued_bytes` 25 MiB).
- **Delivery semantics, MQTT to Kafka: required content of `ARCHITECTURE.md`** (owner, DETENTE 3.3.h, 2026-10-12; wording approved). The benchmark showed Mosquitto dropping messages for the bridge past its per-client queue while acknowledging the publisher (diagnostic at 3000 msg/s: 61,140 dropped, exactly the number missing from `telemetry.raw`); fixed in `baef69b` (queue 60000 messages / 25 MiB) and made visible in `5c225e0` (`mqtt_messages_dropped`). The owner's first wording, "at-least-once from bridge receipt onward", is not exact: a crash loses what the bridge holds. Text to use, in English, as written:

  > **Delivery semantics, MQTT to Kafka**
  >
  > - **Publisher → Mosquitto.** QoS 1. A PUBACK means Mosquitto accepted the message. It does not mean the bridge received it, or ever will.
  > - **Mosquitto → bridge.** QoS 1, clean session, no broker persistence. While the bridge is connected, Mosquitto holds up to 60,000 messages (or 25 MiB of payload) for it. Beyond either bound it drops new messages for the bridge and still acknowledges the publisher: there is no backpressure. Drops are visible: the bridge logs `mqtt_messages_dropped` at ERROR with the count. The counter is broker-wide and updated every 10 s. Messages published while the bridge is not connected are not delivered (no persistent session).
  > - **Inside the bridge.** Each MQTT message is acknowledged on receipt, before Kafka confirms it, and held in memory until produced. A clean stop (SIGTERM, SIGINT) processes and flushes everything received; a crash loses it.
  > - **Bridge → Kafka.** `acks=all` with the idempotent producer: retries neither duplicate nor reorder a record. A record not confirmed within librdkafka's `delivery.timeout.ms` (default 300 s) is logged as `message_delivery_failed`, and the run exits 1.
  > - **In short.** From receipt by a running bridge onward, every message reaches `telemetry.raw` once, unless the bridge crashes or a delivery failure is logged. Before receipt, delivery is at most once, through a bounded buffer with no backpressure; losses at the buffer are logged, losses while the bridge is down are not.

- **Alarm reconciliation runs only at `make up`; a broker restart without it leaves ghost alarms** (owner, 2026-10-03, Task 3.2, option A). Kafka keeps its data on tmpfs and starts empty; ThingsBoard keeps its alarms in a volume. The import script run by `make up` clears every pipeline alarm active in ThingsBoard but not in `telemetry.alarms`, records `cleared_by: reconciliation` and the reason in the alarm's details, and marks the matching `alarm_last` entry CLEARED (`reconcile_alarms`, `scripts/thingsboard/import_rule_chains.py`). If the broker is restarted any other way (for example `docker compose restart broker`, or a container crash and restart), Kafka loses the CLEARED events still to come and nothing reconciles: an active alarm stays active in ThingsBoard and absorbs the next alarm of its type on that asset (the new alarm keeps the old start time). `ARCHITECTURE.md` must state this limitation. Option B, persistent Kafka storage (a volume instead of tmpfs), which removes the cause, is to be reconsidered in STEP 0 of Task 3.3.
- **Delivery into ThingsBoard: what is guaranteed, and what is not** (owner, 2026-10-04, Task 3.2 fix). Document in `ARCHITECTURE.md`, with the delivery semantics of the other hops:
  - Delivery is at-least-once up to ThingsBoard's MQTT transport: the sink stores a record's offset after the PUBACK.
  - ThingsBoard keeps its rule-engine queues in memory (`TB_QUEUE_TYPE: in-memory`, `docker-compose.yml`): a ThingsBoard restart between the PUBACK and the processing loses the message, and nothing re-delivers it (the sink has committed past it).
  - The reconciliation at `make up` clears ghost alarms; it does not restore an alarm that is active in `telemetry.alarms` but missing in ThingsBoard.
  - Within a running ThingsBoard, nothing is dropped silently: the pipeline devices are on the PipelineSequential queue (60 s per batch, 20 retries from 5 s up to 60 s); a message AlarmMapping cannot apply ends in its Failure branch, recorded as `alarm_mapping_failed` on the pipeline gateway (dashboard counter, current month); what the queue gives up on after its retries shows only in ThingsBoard's queue statistics (its log). Before the fix, ThingsBoard's SequentialByOriginator queue (2 s per batch, 3 retries) dropped alarm events: runs 37168739715 and 37227357007, and locally (236 messages, hidden by the replay of the ordering test).
- **The throughput ceiling of the path to ThingsBoard** (owner, 2026-10-04). ThingsBoard processes an asset's messages one at a time; each waits for ThingsBoard's SQL batch writes. Measured on 2026-10-04, one asset, alarm events: 6.9 msg/s with ThingsBoard's default batch delays, 20.2 msg/s at 25 ms (set in `docker-compose.yml`), 43.1 msg/s at 10 ms, with no measurable CPU difference at 20 msg/s. The sink limits each asset to 10 msg/s (`config/thingsboard.yaml`), coupled with the 25 ms delays (stated on both sides; with the defaults the limit must be 3). The ceiling of the ThingsBoard path is therefore 10 msg/s per asset, far below the Kafka path's.
- **After a ThingsBoard outage, new alarms wait behind the backlog** (owner, 2026-10-04). The backlog drains at 10 msg/s per asset, and the sink handles one record at a time, so a new alarm is sent only after the records before it. Measured: a backlog of 3,200 messages of one asset took 320 s (`test_a_backlog_of_one_asset_reaches_thingsboard_without_a_drop`). Calculated, not measured: after a 1-hour outage with 5 assets (18,000 messages), between about 7 minutes (records of all assets interleaved: 50 msg/s in total) and about 60 minutes (records grouped by asset: 10 msg/s in total, against 5 msg/s still arriving).
- **Dashboard limitations from the Task 3.2 fix** (owner, 2026-10-04): no counter of messages ThingsBoard dropped (its QUEUE_STATS entity cannot be selected reliably: the name filter fails on the underscore of `<queue>_<service id>`, there is one entity per container, they cannot be deleted, and one exists only after the first statistics report with messages); the mapping-failures counter counts the calendar month (aggregating cards in ThingsBoard 4.2 take only calendar intervals); ThingsBoard 4.2 does not pass a node's error text on with the failed message, so `alarm_mapping_failed` has no error text: the failed node's debug events (failures only) keep it, and the full-profile session saves them in its artifacts.

## From Task 3.4 (findings while documenting; owner decisions at DETENTE 3.4.a, 2026-10-12)

- **Before the repository goes public: the alarm consumer emits a spurious CLEARED after a restore and a replay (H3).**
  - **Trigger.** A RAISED is acknowledged by Kafka, and the consumer stops before the batch's `telemetry.raw` offsets are committed. On restart the alarm is restored ACTIVE with zeroed counters (`restoreActive`, `processing/alarm_consumer/state_machine.js`), and the replay processes the samples before the raise again.
  - **Effect.** With at least `persistence_samples` of them below the clear level, the consumer emits a CLEARED for the restored `alarm_id`, stamped before the raise, then the same RAISED again. ThingsBoard applies the CLEARED and drops the repeated RAISED and the real clear later, so the alarm shows cleared while the condition holds.
  - **Evidence.** Verified on 2026-10-12 by `tests/integration/test_restore_replay.py` (both tests); result in `docs/internal/phase3_task3.4_h3_result.md`. The tests pin the current behaviour and must change with the fix, together with `docs/ARCHITECTURE.md` (section 6 and limitation 1).
  - **Not decided.** The fix. Candidates to evaluate: for a restored alarm, ignore samples whose `ts` precedes its raise; or keep the RAISED's `source_seq` (a field of `alarm_v1`) and skip that asset's earlier samples. Either must also handle the simulator's `seq` restarting.
- **The bridge's in-memory queue has no bound (H2).** `self.inbox` is an unbounded `queue.Queue` (`bridge/mqtt_to_kafka/__main__.py`). While the producer's local queue is full (`_produce` retries on `BufferError`), the paho thread keeps acknowledging and enqueuing, so memory grows with the input rate and Mosquitto sees no congestion. Read from the code; no test. To decide: a bound with a logged drop, or backpressure by stopping the MQTT read; either needs a test with Kafka unavailable.
- **The alarm consumer supports one instance only (H4).** The state is in memory per asset and rebuilt only at start-up, so a second instance in the group, or a rebalance, would take partitions without their state. Nothing prevents it or says so in the code. To decide: document it in the consumer's module comment and refuse to start a second member, or rebuild the state for the assigned partitions on every assignment.
- **Firebase node (H5).** The REST node PUTs every telemetry message of any device to `${FIREBASE_DB_URL}/temperature.json`, so each message overwrites the same path. `FIREBASE_DB_SECRET` is in `.env.example` and nothing reads it, so the call is unauthenticated. The path was never verified against a live database. To decide: fix the path and the authentication and verify it, or remove the Firebase leg and the two variables.
- **Bridge with Schema Registry down after start-up (H11).** Not verified: the bridge registers its schemas at start-up, and whether its serializer calls the registry again later is not tested (`test_schema_registry_down` covers the alarm consumer). Needs an integration test that stops Schema Registry while the bridge runs.

## Unscheduled (owner: not in Task 3.3)

- **ThingsBoard always stops by SIGKILL; a wrapper with a SIGTERM trap would let it shut down cleanly** (owner, 2026-10-10, DETENTE 3.3.c, option b).
  - **Fact.** The image `thingsboard/tb-postgres:4.2.1.1` has no entrypoint, and its command is `start-tb.sh`, a bash script that runs as PID 1. It calls `start-db.sh`, runs `java …` in the foreground (no `exec`, no `trap`), then `stop-db.sh`. A PID 1 bash with no handler ignores SIGTERM and does not forward it, so Java never sees the stop and `stop-db.sh` never runs.
  - **Verified on 2026-10-10.** After `make up` and `make down` with a 60 s grace period, `docker events` showed SIGTERM, then SIGKILL 60 s later, exit 137.
  - **Current state.** The compose file gives ThingsBoard a 5 s grace period and says why: a longer one only slows `make down`. Postgres does crash recovery on every start.
  - **Option (b).** A wrapper script of our own, mounted read-only as the service's `command`, that:
    1. traps SIGTERM;
    2. starts the database and ThingsBoard as the image does, with Java in the background;
    3. forwards the signal to Java and waits for it;
    4. runs `stop-db.sh`.
    
    It replaces a third-party start-up, so it must be reviewed on every ThingsBoard upgrade.
  - **Verification of (b).** After `make up` and `make down`, `docker events` must show no SIGKILL for the thingsboard container (exit 0 or 143). On the next start, the Postgres log must have no "database system was not properly shut down" line.

- **Task 3.3: the lag-slope tolerance is 0.001 s/s, not 0** (owner, DETENTE 3.3.d). It is `criteria.max_lag_slope_per_s` in `config/benchmark.yaml`, and `bench/report.py --max-lag-slope` recomputes the ladder with another value without new runs.
