# Phase 3 Backlog

Items recorded during Phase 3 for a later task, with where they come from. Phase 2 items that carried over are in `docs/internal/phase2_backlog.md` and in section 8 of the Phase 2 closure report.

## For the design of Task 3.2 (ThingsBoard as the operations layer)

- **The ThingsBoard sink must tolerate tombstones with unknown keys on `telemetry.alarms`** (owner, 2026-10-02). The topic is compacted and keyed by `alarm_id`, and not every record on it is an alarm event: since `f28516f` the integration test `test_restore_after_real_compaction` writes one tombstone per partition with a reserved key (`it-roll-marker/<partition>`) to force a segment roll, and compaction itself turns superseded records into gaps. A tombstone has a null value and a key that need not match any alarm. The sink must skip such records (or treat them as deletions of an alarm it never saw) without failing, without dead-lettering them, and without blocking its consumer group. The alarm consumer's own restore already does this (`readActiveAlarms`: a tombstone deletes the key, a no-op for an unknown one).

## For Task 3.4 (architecture document)

- **A CLEARED event stays in the active segment until the next write to its partition** (owner, 2026-10-02). The broker evaluates `segment.ms` only when it appends to a partition, and the log cleaner never compacts the active segment. So on `telemetry.alarms`, the RAISED record of a cleared alarm is removed only after another record lands in the same partition and closes the segment holding the CLEARED. With alarms keyed by `alarm_id`, which contains a timestamp, which partition receives the next write is chance; on a quiet partition the RAISED/CLEARED pair can stay uncompacted indefinitely. This is not a correctness problem (readers keep the latest event per `alarm_id`, and the restore reads the CLEARED), but it means compaction does not bound the topic's size by time. Verified on 2026-10-02 on a scratch topic with `segment.ms` 1000 (no roll in 40 s without writes; the old record gone about 20 s after one unrelated write); root cause of the CI failure of run 37070295558, fixed in `5b28fd1`. `ARCHITECTURE.md` should state it under delivery semantics or the compaction policy, with the broker settings that govern it (`segment.ms`, `min.cleanable.dirty.ratio`, `log.cleaner.backoff.ms`).
- **`telemetry.alarms` is keyed by `alarm_id` but partitioned by asset** (owner, 2026-10-03, Task 3.2). The alarm consumer's producer uses `AssetPartitioner` (`processing/alarm_consumer/consumer.js`): the key stays the `alarm_id`, which compaction and the state restore need, while the partition is the default murmur2 partition of the `asset_id` (the key's first segment). Kafka orders records only within a partition, and the ThingsBoard sink's alarm mapping needs an asset's alarm events in production order: it applies an event only if it is newer than the last one applied for that asset and alarm type. With the default partitioner (partition from the whole `alarm_id`) an asset's alarms spread over partitions and a lagging or replaying reader drops older alarms; measured in Task 3.2 before the change: 19 of 48 alarms kept after a replay. Any other producer writing to `telemetry.alarms` must partition the same way. `ARCHITECTURE.md` should state this contract next to the compaction policy; dead letters from the consumer follow the same rule (keyed by `asset_id`).
- **`make run` keeps the pipeline running until it is stopped** (owner, 2026-10-03, review of Task 3.2). For STEP 0 of Task 3.4: the processes (sink, alarm consumer, bridge, simulator) must run until stopped, with no short `--duration`. The Task 3.2 review instructions used `--duration 1200`, and the consumer and the bridge stopped in the middle of the owner's review.
- **A simulator QoS 1 acknowledgement means Mosquitto accepted the message, not that the bridge got it** (owner, observed live 2026-10-03). With the bridge down, the simulator reported 600 messages sent and acknowledged and none reached Kafka. Why: Mosquitto runs with `persistence false`, and the bridge connects with a clean session (paho's MQTT 3.1.1 default, `clean_session=True`) under a client id that contains its process id, so no session outlives it; with no subscriber connected, the broker accepts each QoS 1 publish (the PUBACK the simulator counts) and drops it. `ARCHITECTURE.md` must state this hop's semantics: delivery from the simulator to Mosquitto is acknowledged, delivery from Mosquitto to the bridge happens only while the bridge is connected. A persistent session (fixed client id, `clean_session=False`, Mosquitto persistence on) would queue messages while the bridge is down, up to Mosquitto's queue limits; not implemented, listed with the other known limitations of the bridge (manual MQTT acknowledgement).
- **Start-up warnings: what they are, and the decision** (owner question, 2026-10-03). Document both in `ARCHITECTURE.md`:
  - `AuthlibDeprecationWarning: The httpx module is deprecated; please use httpx2 instead` (sink and bridge, logged as JSON). `confluent-kafka[schemaregistry]` 2.15.1 depends on `authlib` (OAuth for Schema Registry, unused here) and imports its httpx integration; Authlib 1.8.0 deprecated its fallback to `httpx` and warns when `httpx2` is not installed. Harmless here. It appeared without any change in the repository because `authlib` is a transitive dependency with no pin: the Python side has no lock file, unlike `package-lock.json`. Decision: documented, not filtered (a filter would also hide the next real deprecation); pinning the full Python dependency tree is a Task 3.6 item (below).
  - kafkajs `Limiting retries for the idempotent producer may invalidate EoS guarantees` (alarm consumer). Intended and already explained in `createProducer` (`processing/alarm_consumer/consumer.js`): retries are bounded on purpose so that a send that keeps failing fails the handler and the consumer stops without committing; nothing relies on producer exactly-once. Decision: documented, not changed.
  - (`TimeoutNegativeWarning` from kafkajs on Node.js 24: already decided, Phase 2 backlog.)
- **The dashboard's charts draw a straight line across a period without data** (owner, 2026-10-04, Task 3.2). When the pipeline stops and starts again (a `make up`, a process stopped), the time-series chart joins the last point before the gap to the first after it. Not configurable in ThingsBoard 4.2.1.1, verified: the widget's line settings, as its own UI code builds them, are `showLine`, `step`, `stepType`, `smooth`, `lineType`, `lineWidth`, point and label options and `fillArea`, with no gap option; and with aggregation the REST API returns no entry for an empty interval (pump-01, AVG per minute over 23:38-23:48 UTC on 2026-10-03: no value for 23:42-23:44, rather than an empty one), so the chart has nothing to break the line on. Not forced (owner decision). `ARCHITECTURE.md` lists it with the dashboard's known limitations; for captures, wait until the chart window holds no gap (10 minutes of continuous data with the default window).
- **Alarm reconciliation runs only at `make up`; a broker restart without it leaves ghost alarms** (owner, 2026-10-03, Task 3.2, option A). Kafka keeps its data on tmpfs and starts empty; ThingsBoard keeps its alarms in a volume. The import script run by `make up` clears every pipeline alarm active in ThingsBoard but not in `telemetry.alarms`, records `cleared_by: reconciliation` and the reason in the alarm's details, and marks the matching `alarm_last` entry CLEARED (`reconcile_alarms`, `scripts/thingsboard/import_rule_chains.py`). If the broker is restarted any other way (for example `docker compose restart broker`, or a container crash and restart), Kafka loses the CLEARED events still to come and nothing reconciles: an active alarm stays active in ThingsBoard and absorbs the next alarm of its type on that asset (the new alarm keeps the old start time). `ARCHITECTURE.md` must state this limitation. Option B, persistent Kafka storage (a volume instead of tmpfs), which removes the cause, is to be reconsidered in STEP 0 of Task 3.3.
